# 原始需求文档：渐进式 AI 决策支持系统

## 1. 文档目的

本文档用于固化当前阶段已经明确的产品方向、边界和第一版需求，用作后续持续分析开源项目、拆分功能、设计 GUI 和规划后台系统的基线文档。

当前结论不是最终定版，而是后续选型和迭代的统一参照。

## 2. 产品定位

### 2.1 核心定位

本项目要做的不是通用聊天助手，也不是单纯的 AI 编码框架，而是一个：

**面向内部需求梳理与产品意图理解场景的、分阶段推进的 AI 决策支持工作台。**

### 2.2 一句话定义

系统接收一个模糊问题、需求、想法或调研目标，经过多阶段的引导、发散、评估、对照和收敛，最终输出**可解释的决策建议**，并沉淀全过程数据到后台。

### 2.3 产品阶段

- 第一阶段：内部使用，优先服务开发者自己，用于梳理需求、理解产品意图、分析调研材料、形成决策建议
- 第二阶段：推广给项目经理、产品经理及其他业务角色使用
- 第三阶段：基于后台沉淀的数据，形成组织级知识库、经验库和 idea 提炼能力

## 3. 当前确认的核心原则

- 主输出优先级：`决策建议`
- 支撑输出：`需求简报`、`调研结论`
- 决策方式：不追求一次性吐大量答案，而是采用**渐进式 ideation**
- 产品形态：前台优先做 GUI，后台需要具备数据收集、管理和提炼能力
- 研究方式：后续分析开源项目时，必须围绕本项目需求做贴近分析，而不是机械罗列功能

## 4. 目标用户

### 4.1 第一阶段目标用户

- 内部开发人员
- 用于需求梳理、产品理解、方案探索、调研汇总和决策辅助

### 4.2 第二阶段扩展用户

- 项目经理
- 产品经理
- 其他需要参与方案讨论、需求判断和项目决策的角色

### 4.3 用户核心痛点

- 原始问题往往模糊，缺少结构化定义
- 头脑风暴容易发散，缺少阶段化推进
- 调研材料分散，难以形成可复用结论
- 决策过程不可追溯，后续复盘困难
- 现有 AI 工具往往只给“答案”，不提供清晰的过程和依据

## 5. 第一版产品目标

### 5.1 主目标

让用户可以把一个模糊问题推进成：

1. 可理解的问题定义
2. 有证据支撑的调研结论
3. 有比较依据的候选方案
4. 最终的决策建议

### 5.2 第一版不追求的目标

- 不做通用型“万能 AI 助手”
- 不做复杂的自治公司系统
- 不把重点放在代码生成上
- 不一开始就做过重的多代理自治调度
- 不追求一次覆盖所有角色和所有业务场景

## 6. 第一版主输出与支撑输出

### 6.1 主输出：决策建议

第一版系统的最终主输出物应包括：

- 问题定义
- 候选方案列表
- 每个方案的优缺点
- 风险与约束
- 推荐方案
- 推荐理由
- 待确认事项
- 下一步建议动作

### 6.2 支撑输出一：需求简报

需求简报用于描述：

- 原始问题
- 背景
- 目标
- 用户角色
- 约束条件
- 非目标
- 成功标准

### 6.3 支撑输出二：调研结论

调研结论用于描述：

- 调研对象
- 证据来源
- 核心发现
- 可借鉴部分
- 不适合借鉴部分
- 对当前产品的启发

### 6.4 三者关系

本系统不是在三种输出里三选一，而是形成一条链路：

`需求简报 -> 调研结论 -> 决策建议`

其中：

- `决策建议` 是主输出
- `需求简报` 和 `调研结论` 是支撑主输出的过程产物

## 7. 核心流程设想

### 7.1 总体流程

建议第一版围绕以下四个核心阶段设计：

1. 问题定义阶段
2. 调研与发散阶段
3. 方案比较与评估阶段
4. 决策收敛阶段

### 7.2 阶段说明

#### 阶段一：问题定义

目标：

- 把原始输入从模糊描述变成结构化问题

系统动作：

- 追问必要上下文
- 提取目标、约束、非目标、角色、成功标准
- 形成需求简报

阶段输出：

- 问题定义
- 需求简报

#### 阶段二：调研与发散

目标：

- 基于已定义问题，扩展候选方向和外部参考

系统动作：

- 分析已有资料和用户提供的开源项目
- 检索相似产品、框架、案例
- 提取可借鉴的流程、架构、产品设计和数据能力
- 形成初步候选思路

阶段输出：

- 调研结论
- 候选方向清单

#### 阶段三：方案比较与评估

目标：

- 不只列方案，而是比较方案

系统动作：

- 建立对比维度
- 对各方案进行优缺点分析
- 给出风险、依赖、实现复杂度、适用性判断

阶段输出：

- 对比矩阵
- 风险评估
- 推荐候选集

#### 阶段四：决策收敛

目标：

- 给出当前阶段最合理的决策建议

系统动作：

- 综合前述信息
- 明确推荐方案
- 标注建议依据与未确认项
- 生成下一步行动建议

阶段输出：

- 决策建议
- 下一步建议

## 8. 与 MIDAS 思路的契合点

本项目当前最契合的理论支撑，是 MIDAS 提出的**渐进式 ideation**。

对本项目真正有价值的不是其“13 个 agent”的具体形式，而是以下方法论：

- ideation 不应是一次性大量输出，而应是分阶段推进
- 人不是被动筛选器，而应是参与式、主动式合作者
- 生成和评估应形成连续反馈循环，而不是先堆大量想法再人工筛
- 好的系统要同时考虑本次候选方案之间的差异，以及它们与外部现有方案的差异
- 过程应保留“从想法到结论”的演化链路，而不是只保留最终答案

对本项目的实际启发：

- 前端流程设计应是阶段式工作台，而不是单一聊天窗口
- 系统应允许用户在中途插入自己的判断、修正和新想法
- 需要把“调研结论”和“候选方案比较”纳入主链路，而不是做成附属能力

## 9. 对现有参考项目的初步借鉴方向

### 9.1 AegisFlow

优先借鉴：

- 从模糊想法推进到结构化产物的阶段式流程
- 多阶段产物沉淀
- 评审和收敛机制

重点参考：

- 前四阶段能力，而不是完整开发流水线

### 9.2 Trellis

优先借鉴：

- 规范化上下文管理
- 长期记忆和过程沉淀
- 任务/上下文/规范的组织方式

重点参考：

- 如何让系统长期可维护，而不是一次性输出文档

### 9.3 Paperclip

优先借鉴：

- GUI 管理台思路
- 任务、目标、过程、状态的可视化管理
- 后台治理、审计、追踪、预算/成本意识
- 多实体、多角色、多会话的数据组织方式

不直接照搬：

- “零人公司”定位
- 过重的组织编排和自治系统

本项目对 Paperclip 的吸收方向应是：

- 借鉴其**控制台和治理思维**
- 不照搬其“自治公司”产品目标

## 10. GUI 初步设想

### 10.1 第一版界面目标

GUI 不是装饰，而是为了：

- 降低使用门槛
- 提升推广性
- 让阶段流程、候选方案、证据和决策更容易理解

### 10.2 建议的界面骨架

第一版可以考虑以下页面结构：

#### 1. 工作台首页

- 当前项目/话题列表
- 最近会话
- 最近输出的决策建议
- 调研任务入口

#### 2. 决策会话页

- 左侧：阶段导航
- 中间：当前阶段的交互区与结果区
- 右侧：上下文摘要、候选方案、关键证据、当前结论

#### 3. 调研分析页

- 开源项目/资料卡片
- 对比维度
- 启发点
- 可借鉴/不建议借鉴项

#### 4. 决策结果页

- 推荐方案
- 备选方案
- 依据说明
- 风险项
- 待确认事项
- 下一步建议

#### 5. 后台管理页

- 用户行为统计
- 常见问题分布
- 决策主题分类
- 过程转化漏斗
- 高价值 idea 汇总

## 11. 后台系统需求

### 11.1 后台目标

后台不只是日志存储，而是要支持：

- 行为留痕
- 过程追踪
- 结果复盘
- idea 提炼
- 组织级知识沉淀

### 11.2 第一版建议采集的数据

#### 用户与会话维度

- 用户身份
- 角色类型
- 会话时间
- 会话主题
- 会话阶段流转记录

#### 输入与过程维度

- 用户原始问题
- 系统提出的关键追问
- 用户补充的信息
- 阶段结果快照
- 候选方案的变化过程

#### 输出维度

- 需求简报
- 调研结论
- 决策建议
- 最终被采纳的方案
- 未采纳原因

#### 分析维度

- 高频问题类型
- 常见决策路径
- 常被引用的开源项目
- 常见被采纳的启发点
- 易卡住的阶段

### 11.3 后台后续可扩展能力

- 自动聚类相似问题
- 自动提炼高价值 idea
- 形成组织级“决策模式库”
- 反向优化提示词、流程和评估维度

## 12. 第一版建议的数据对象

建议第一版至少围绕以下对象建模：

- `User`
- `Workspace`
- `Session`
- `StageRun`
- `ResearchItem`
- `Evidence`
- `CandidateOption`
- `DecisionRecommendation`
- `Insight`

这些对象的关系应能表达：

- 一个用户在一个工作空间下发起多个会话
- 一个会话包含多个阶段
- 每个阶段产生中间产物
- 中间产物可关联外部证据和候选方案
- 最终会话收敛为一个决策建议

## 13. 第一版功能边界建议

### 13.1 应优先做

- 结构化问题定义
- 阶段式会话流程
- 调研材料管理
- 候选方案比较
- 决策建议生成
- 后台数据沉淀

### 13.2 可以后置

- 复杂多代理自治
- 自动长时运行
- 组织级权限体系细化
- 高级知识库
- 自动化外部系统集成
- 多租户商业化能力

## 14. 后续分析开源项目的评估准则

后续你继续给出开源项目时，分析必须统一围绕以下问题展开：

1. 这个项目解决的核心问题是什么
2. 它的产品定位和我们的目标是否同向
3. 它在哪个阶段最有借鉴价值
4. 它的界面、流程或架构，哪些适合吸收
5. 哪些能力虽然强，但不适合当前阶段
6. 如果吸收它，应该放入我们的哪一阶段
7. 它对 GUI、后台、数据采集、决策收敛分别有什么启发

输出时应尽量形成：

- 可借鉴
- 暂不借鉴
- 原因
- 可落位阶段

## 15. 当前风险与待确认项

### 15.1 当前风险

- 如果阶段定义过多，第一版可能过重
- 如果只强调决策建议，容易出现“建议缺少证据支撑”
- 如果后台数据模型设计过晚，后续难以复盘和提炼
- 如果 GUI 只做聊天样式，无法体现阶段式工作台价值

### 15.2 待确认项

- 第一版更偏“需求梳理”还是更偏“调研决策”
- 决策建议的评价维度如何定义
- 哪些外部来源需要优先接入
- 后台首先服务运营统计，还是服务知识提炼
- GUI 第一版是单页工作台还是多页结构

## 16. 当前建议结论

基于当前已确认信息，第一版产品建议按以下原则推进：

- 产品主线：`需求梳理 -> 调研分析 -> 方案比较 -> 决策建议`
- 主输出：`决策建议`
- 支撑输出：`需求简报`、`调研结论`
- 前台形态：GUI 工作台
- 后台定位：过程数据沉淀与提炼中心
- 参考方向：吸收 AegisFlow 的阶段流程、Trellis 的上下文治理、Paperclip 的管理台思维、MIDAS 的渐进式 ideation 方法论
